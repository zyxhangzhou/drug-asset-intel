## Context

- 快照是只读 SQLite（`data/processed/intel.db`），由 `intel build` 生成；应用以只读连接打开（`app-runtime`）。
- 业务值在实体表的类型化列中；来源在 `claim`（`entity_type, entity_id, field`）与 `source`。`entity_type` 等于表名，`entity_id` 为主键字符串。
- 现有 API：`/api/health`、`/api/meta`、`/api/shortlist`（`src/intel/api.py`）。前端：Vite + React 19 + Ant Design 6，只有一个概览页，没有路由。
- 数据量：候选 149 家（主组合 133 条）、试验 3205 项（单家最多 288 项）、声明约 6.8 万条。来源 3891 条，其中有存档文本（`.txt`）的只有文档抽取用的十几份；其他来源的本地路径是 JSON / xlsx 原始响应，或没有本地文件（CT.gov）。

## Goals / Non-Goals

**Goals:**

- 演示主线一次走通：买方 → 偏好 → 匹配候选 → 公司 → 管线 → 试验 → 结果 → 来源原文。
- 任何带来源的值都能在一次点击内看到来源声明（事实 / 推断、置信度、原文片段）。

**Non-Goals:**

- 服务端分页、全文检索、缓存层：数据量小，单次查询即可。
- 移动端专门布局：保证窄屏可用，不做单独设计。
- 前端单元测试框架：用类型检查与浏览器走查验证。

## Decisions

### 1. 接口按页面组织，响应模型集中定义

新接口：

- `GET /api/buyers`：买方列表（代码、名称、中文名、偏好行数、最佳匹配公司数）。
- `GET /api/buyers/{ticker}`：画像字段、偏好行、财务、专利到期产品、匹配分前 15 的候选（Match）。
- `GET /api/targets/{ticker}`：公司、入选理由、主组合与其他组合的复核结论、管线（药物 → 适应症）、获批产品、催化事件、最新财务快照、试验摘要、全部试验结果。
- `GET /api/trials/{nct}`：试验全部字段、所属公司与适应症、结果。
- `GET /api/sources/{source_id}`：来源元信息、存档文本是否可读、引用该来源的声明数。
- `GET /api/sources/{source_id}/text`：存档文本（纯文本）。

查询放进新模块 `src/intel/views.py`（返回 pydantic 模型），`api.py` 只做路由。备选是把查询写在路由函数里；`api.py` 会膨胀到难读，所以拆开。

### 2. 来源声明批量取回，挂在实体上

每个实体模型带 `sources: dict[str, list[ClaimOut]]`。一个请求内先收集所有 `(entity_type, entity_id)`，按实体类型一次 `IN` 查询取声明并联表取来源，再分发到实体。备选是前端按需请求每个字段的来源：点击才发请求，交互延迟高，接口也多一个，不采用。

### 3. 存档原文的安全读取

`/text` 只在来源的 `local_path` 以 `.txt` 结尾、解析后的绝对路径位于项目 `data/raw/` 目录内时返回内容，否则 404。路径不接受用户输入，只读快照里的记录，仍做目录检查防止快照被篡改后读到任意文件。前端在原文中用声明的片段做规范化匹配（空白与引号差异不计），标出位置并滚动到第一处；找不到时提示「片段未在原文中定位」。

### 4. 前端路由与深链接

前端加 `react-router`（BrowserRouter），路由：`/`、`/buyers`、`/buyers/:ticker`、`/targets`、`/targets/:ticker`、`/compare?t=A,B`、`/trials/:nct`、`/sources/:id`。后端把非 `/api` 且非静态文件的请求返回 `index.html`。备选 HashRouter 不需要后端改动，但链接不规范、无法与来源页 URL 对齐，不采用。

### 5. 来源标记组件

一个通用组件 `<Sourced claims={...}>值</Sourced>`：值旁一个小标记，颜色区分事实 / 推断 / LLM；悬停或点击弹出声明列表（来源标题、类型、日期、片段、置信度），每条有「来源页」与「原网址」链接。没有声明时不显示标记。

### 6. 候选列表在前端筛选与对比

`/api/shortlist` 一次返回全部主组合（133 行），筛选、搜索、排序在前端做；调权重时重新请求接口。对比最多 4 家，状态写进 URL 查询参数，可分享。

### 7. 视觉：简洁的数据产品风格

评审在自己电脑上细读，也会投屏讲解。第一轮做了投研报告风（衬线、米白纸面），用户评审后选择更有科技感的无衬线方案：冷灰底、白色面板、钴蓝一种强调色；来源标记保留三色（事实 / 推断 / LLM）。中文字体（思源黑体）随前端打包，按 Unicode 区段切片，浏览器只下载用到的切片，因为评审所在网络可能无法访问 Google Fonts，且各系统默认中文字体不同。

长文本（复核字段、画像、偏好证据）只在显示层排版：按句号分段、英文原文引用成块、来源 ID 变链接、关键数字加粗。文字内容不改，入库校验与快照不受影响。

## Risks / Trade-offs

- [单家公司试验多（288 项），详情响应大] → 公司详情只返回试验摘要，不带声明；试验声明在试验详情返回。
- [前端没有单元测试] → `npm run build` 做类型检查；按演示主线做一次浏览器走查并截图记录。
- [管线来自 CT.gov 推导，名称噪声大] → 页面标明「管线由 CT.gov 推导（推断）」，与签字的机制 / 类型来源区分显示。
